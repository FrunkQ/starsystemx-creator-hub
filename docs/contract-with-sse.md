# The contract with Star System Explorer

The hub reads a format another repository writes. This file records what that contract actually is,
and — more usefully — the five things about it that were **not** obvious from the design document
and cost real time to work out.

The design (`creator-hub-design.md` §4) is right that the coupling is small: the hub never *uses* a
campaign. It opens a zip, reads one JSON, cuts it into rows, lists asset paths and reads the
provenance flags. The constants are mirrored in `src/lib/bundle/contract.ts` rather than imported,
for the reasons §4 gives.

---

## C-01. Images are NOT content-addressed in the bundle. Only models are.

The design's §3.4 says *"assets are already keyed by sha256"* and the build brief repeats it. That
is true of **models** and not of images:

```
assets/models/<sha256>.glb                <- content hash
assets/images/<nodeId>.<ext>              <- a NODE ID, not a hash
assets/images/player/<assetId>.<ext>      <- an ASSET ID, not a hash
```

The entire per-hash moderation economy (§6.1) is about **images** — *"manual pic review"*, the porn
problem, *"checked ones never appear again"*. So the property the moderation design leans on does
not arrive with the bundle for the assets that need it most.

**This is not a problem, but it is a different mechanism than the design implies.** The hub computes
sha256 itself from the bytes, for every asset, model and image alike. It is one `crypto.subtle.digest`
call per member and it happens anyway (see C-03). Everything §3.4 and §6.1 promise still holds —
cross-user dedup, HEAD-and-skip, immutable caching, the shrinking queue — it is just the hub doing
the hashing rather than inheriting it.

**Consequence worth knowing:** two creators who upload the same picture attached to *different
nodes* still dedup, because the hub keys on bytes and not on the bundle path. Under the path-derived
reading they would not have.

---

## C-02. The public-sharing gate must be computed from the DOCUMENT, never read from `ATTRIBUTIONS.md`

`ATTRIBUTIONS.md` is generated by the engine, it contains the literal string `_No provenance
recorded._`, and it prints a count of how many assets are missing provenance. It is extremely
tempting to read the gate straight off it.

**That would be a gate anybody could open.** `ATTRIBUTIONS.md` is a file inside a zip that a stranger
uploaded. Deleting nine lines of markdown from it passes the gate while the assets underneath stay
completely uncredited.

The engine's own header calls it a **working document** for a GM to read. It was never a control
surface, and the moment a second codebase treats it as one, it becomes one.

So `src/lib/bundle/attribution.ts` mirrors `collectAttributions` and recomputes `missing` from the
node fields. `ATTRIBUTIONS.md` is still shown to the reviewer — as **the creator's claim**, beside
the image, which is exactly how §6.4 frames it for review. The gate treats it the same way.

---

## C-03. A path-supplied hash is attacker-controlled, and trusting it forges a moderation verdict

This is the most dangerous way to get the ledger wrong.

A model lives at `assets/models/<sha256>.glb`. If the hub keys R2 and the ledger on the hash **read
out of that path**, then a crafted bundle can name its file after a hash that is already `approved`
while carrying entirely different bytes — and those bytes inherit the approval. They are served
immediately, without review, under somebody else's verdict.

It silently converts *"approved once"* into *"approved anything"*, and it would not show up in any
normal test, because a well-formed bundle's path hash always matches.

**The rule: the hub hashes the bytes, always. A path's hash is a claim to be verified, never a key.**
`src/lib/bundle/hash.ts` exists for this and `ingest.ts` refuses a bundle whose model paths disagree
with its bytes. `tests/zip.test.ts` covers the mismatch case.

**The same hole exists in the presigned-upload design** the owner's plan describes — see
`decisions.md` D-04.

## C-04. The engine already tolerates a referenced-but-absent asset, which makes withholding cheap

§6.2 requires that an unreviewed asset is withheld from the **download** too, not just the page. The
obvious worry is that removing a file from the zip leaves the document pointing at something that is
not there.

The engine already handles exactly that, on purpose. From `io/bundle.ts`:

- node images — *"referenced but absent: honest blank, not a broken img"* → it deletes `node.image`
- player assets — *"referenced but absent: leave the path, so the loss is visible not silent"*

So **withholding an asset needs no surgery on the document.** Omit the file; the engine degrades
gracefully on open, as its authors intended for a hand-edited save. `src/lib/server/pack.ts` does
nothing more than filter members and append a note to `README.txt`.

## C-05. The zip reader is mirrored, but hardened — the engine reads trusted input and the hub does not

`src/lib/bundle/read.ts` mirrors the engine's `import/shared/zip.ts` central-directory walker rather
than using `fflate.unzipSync`, for the reasons the engine's own comment gives (ZIP64 sentinels read
as a literal 4 GB; eager decompression of members nobody wants).

What the hub adds, because the engine reads a file the user already trusts on their own machine and
the hub reads whatever a stranger posted:

| added | why |
|---|---|
| path traversal / absolute paths refused | `../../etc/passwd` inside a zip |
| member count capped | a zip with a million entries |
| **total uncompressed size capped, checked against the DECLARED size** | a 50 MB upload can declare terabytes; this fails a check instead of an allocation |
| per-member compression ratio capped | the classic zip bomb |
| `.svg` not accepted as an image | it is script-bearing |

None of this belongs in the engine. All of it belongs here.

## C-06. App-shipped assets are referenced by PATH, not by hash — and that is correct

Validated against seven real saves, 2026-08-28. A node's artwork comes in more shapes than the
bundle layout suggests:

| what | looks like | carried in the bundle? |
|---|---|---|
| a GM's uploaded picture | `assets/images/<nodeId>.jpg` | yes |
| a GM's uploaded model | `assets/models/<sha256>.glb`, node has `model.hash` | yes |
| **an app-shipped star image** | `/images/star_types/M.webp` | **no — it ships with SSE** |
| **an app-shipped starter model** | `/models/nasa/iss.glb`, node has `model.url` and **no `hash`** | **no** |
| someone else's hosting | `https://…` | no |

The real Local Neighbourhood starmap has **60 nodes with images and one with a model, and not one
of them is a carried asset.** They are all app-shipped or remote.

**The hub ignores all three of the non-carried kinds, and should.** It is not hosting those bytes,
so there is nothing to store, nothing to moderate and nothing to credit — the engine's own rule,
that *"a remote url is someone else's hosting and is not ours to credit"*, extends naturally to the
app's own artwork.

**Two things to know because they are surprising:**

1. **`node.model.hash` exists only for GM-uploaded models.** A starter model uses `model.url`. Code
   that assumes `hash` will silently skip them — which is the right outcome here, but only by luck,
   so it should be by intent.
2. **A starter model still carries `credit`, `license` and `sourceUrl`** (the ISS model is credited
   to NASA, public domain). Those never reach the hub's attribution list. That is correct — but if a
   page should ever say *"uses NASA's ISS model"*, that is where the data is.

## C-07. A screenshot the app took is exempt from "missing provenance" — and from nothing else

Engine v3.0.263 (rule DATA-R35). A `PlayerAsset` can carry `capturedInApp: true`: the app rendered
the map to a picture and stored it as one of the campaign's own graphics. The engine's
`attributions.ts` exempts such an asset from the missing-provenance total, and **the hub must
mirror that or the two sides disagree about the same file** — which they did, for two days.

**Why the exemption is right, in the owner's words:** *"a screenshot represents the FILE and the
FILE has the attributions — so anything that COULD be credited is, even if accidentally caught in
shot."* The bundle is the unit of distribution; `ATTRIBUTIONS.md` rides inside it; whatever art a
shot happens to show is credited on the page beside it.

**Why it matters here:** the public gate is `missing.length === 0`, and a blank asset counts toward
`missing`. Without the mirror, a creator who captured a beauty shot of their OWN map — the exact
thing R-07 asked them to do — is refused permission to publish it. Blocked by their own screenshot,
after the app told them it was fine.

**The exemption is for an absence only.** A capture that claims CC-BY and names nobody is still a
breach: a licence that states an obligation and then fails it is wrong whoever took the picture.
And it exempts a literal `true` only — the field is a claim like every other, no weaker than the
credit fields a hand-edited save could equally fill with a fiction, and no stronger.

`noProvenance` in `src/lib/bundle/attribution.ts` is the ONE definition, used by both the gate and
the reviewer's card, so those two can never disagree about what "missing" means.

## The mirrored surface, in full

| what | where |
|---|---|
| `assets/models/`, `assets/images/`, `assets/images/player/` | `contract.ts` |
| `starmap.json` / `system.json`, `ATTRIBUTIONS.md`, `README.txt` | `contract.ts` |
| the magic-number sniff (`PK\x03\x04`), never the extension | `contract.ts` `isZip` |
| node fields sliced: `id`, `name`, `kind`, `roleHint`, `parentId`, `tags` | `normalise.ts` |
| asset refs: `node.image.url`, `node.model.hash`, `playerAssets[].dataUrl` | `attribution.ts`, `normalise.ts` |
| provenance fields: `title`, `credit`, `license`, `sourceUrl`, `capturedInApp` | `attribution.ts` |
| the stamps: `bundleFormat`, `appVersion`, `baseMapVersion`, `revision`, `exportMode` | `format.ts`, `provenance.ts` |
| the creator's cover: `coverAssetId` → `playerAssets[].dataUrl` | `ingest.ts` `pickCover` |

**One trap carried over verbatim:** `assets/images/player/` *starts with* `assets/images/`, so any
match on the image directory must exclude player images **explicitly** rather than by luck. The
engine's comment says so; the mirror repeats it; `tests/provenance.test.ts` covers it.
